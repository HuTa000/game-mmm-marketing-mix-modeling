# 阶段 4 · LLM 自动报告工作流

> 目标：把「结构化模型结果」自动转成「业务方能直接读的决策报告」，
> 同时**保证一个数字都不编**。

---

## 一、业务问题：分析师的时间黑洞

阶段 2 和阶段 3 产出的是一堆后验分布表、森林图、分配矩阵。业务方（市场负责人、CEO）不会读这些。
分析师真正要交的是**一页纸能看懂的决策报告**。但现实是：

| 痛点 | 具体表现 |
|---|---|
| 慢 | 手工写一份 1~2 小时，数据一更新就要重写 |
| 易漏 | 忘了写"可信区间"，或把"模型口径"当成"财务口径"报出去 |
| 不敢交给大模型 | 直接让 LLM 读表格写报告，它会**编数字** |

**LLM 编数字的典型形式**（都是真实发生过的）：

- 把事实里的 `14.37%` 写成 `43.7%`（数字记错）
- 编造事实里不存在的外部基准：「行业平均 ROI 约为 4.2」
- 自行做四则运算得出一个没在数据里的值

这类错误**致命**：业务方按错误数字做预算决策，就是事故。所以本阶段真正的命题不是
"接个 API 让它写报告"，而是：

> **如何在保留 LLM 表达能力的同时，把它的幻觉风险关进笼子。**

---

## 二、核心设计：数字与叙事分离

整个架构只围绕一条原则：**确定性代码负责算数，LLM 只负责表达**。

```
  各阶段产物(CSV)
        │
        ▼
  ┌─────────────────────┐
  │  report_facts.py     │  ← 唯一数字源（可审计）
  │  ReportFacts         │
  └──────────┬──────────┘
             │
             ├──► stage4_facts.json      （全量事实，人可查）
             │
             ├──► allowed_numbers()      （数字白名单）
             │        │
             ▼        ▼
      ┌──────────────────────┐
      │ report_prompts.py    │  组装提示词（facts 是唯一被允许引用的数字）
      └──────────┬───────────┘
                 ▼
      ┌──────────────────────┐     失败/超时/未配置
      │  llm_client.py       │ ─────────────────────┐
      │  (OpenAI 兼容 HTTP)  │                      │
      └──────────┬───────────┘                      │
                 │ 返回文本                          │
                 ▼                                  ▼
      ┌──────────────────────┐            ┌──────────────────┐
      │  report_guard.py     │            │ report_templates │
      │  逐数字对照白名单      │            │   模板降级渲染     │
      └──────────┬───────────┘            └────────┬─────────┘
                 │                                 │
         ┌───────┴────────┐                        │
         │ 通过            │ 违规                    │
         ▼                ▼                        │
   采用 LLM 文本   注入违规清单重试 1 次              │
                        │                         │
                  仍违规 ▼                         │
              降级为模板 + 另存被拒稿 ───────────────┘
                        │
                        ▼
              stage4_report.md（含数字校验审计块）
```

**三条铁律**：

1. 报告里出现的每一个数字，都必须能在 `stage4_facts.json` 里找到（或其合法单位换算）。
2. LLM 输出的每个数字都要过白名单校验，**分级判定**而不是"过/不过"。
3. 校验不通过时，**宁可要一份朴素但正确的模板报告，也不要一份漂亮但数字错的 LLM 报告**。

## 三、五个关键设计决策

### 决策 1：事实层（ReportFacts）作为唯一数字源

`report_facts.py` 从各阶段 CSV 读数据，构建 10 个字段组：

| 字段 | 内容 | 用途 |
|---|---|---|
| `meta` | 数据周期、周数、总花费、真值媒体占比 | 报告背景 |
| `model_quality` | R-hat、ESS、参数个数 | 可信度背书 |
| `optimization` | 预算、当前/优化贡献、增量、可信区间、提升幅度 | 核心结论 |
| `allocation` | 各渠道当前→建议预算、变化% | 建议表 |
| `marginal` | 边际回报 + 可信区间 + 平均 ROI | 诊断表 |
| `roi` | 各渠道 ROI + CI + 真值 | 准确性验证 |
| `elasticity` | 7 档弹性 → 提升幅度 | **决策核心** |
| `scenarios` | 预算 ±20% 的分配 | 敏感性 |
| `robustness` | 后验样本重复优化的分布 | 稳健性 |
| `risks` | 10 条局限声明（含 severity） | 边界披露 |

**为什么不用原始 CSV 直接喂 LLM**：原始表是"数据"，不是"事实"。
比如 `stage3_allocation.csv` 里有 `1557607.151781754` 这样 15 位小数，
LLM 会随手四舍五入成 160 万（偏差 2.7%），而业务方无法判断这是"舍入"还是"编造"。
fact 层统一格式化为**有意义的精度**（金额万元 1 位小数、比例 2 位小数），从源头减少误差。

### 决策 2：白名单校验 + 三级判定

`report_guard.py` 用正则抽出报告里的每个数字，逐个对照白名单：

| 级别 | 相对误差 | 处理 |
|---|---|---|
| `exact` | < 0.3% | 通过 |
| `rounded` | < 1.0% | 通过，但**标注**"存在舍入偏差" |
| `fabricated` | > 1.0% | **违规**，触发重试/降级 |

**为什么容差这么紧**（这是实测校准出来的，不是拍脑袋）：

| 场景 | 实测相对误差 |
|---|---|
| 真实舍入：`4760.6769` → 「4760.7 万元」 | 0.0005% |
| 真实舍入：`14.3716` → 「14.4%」 | 0.2% |
| **编造**：`14.37` → 「43.7%」 | **204%** |
| **编造**：把真实的 4760 万写成 6455 万 | 18.6% |

真实舍入都在 0.3% 以内，编造数字都在 8% 以上。0.3%/1.0% 的分界线**两边都留了充足余量**。

### 决策 3：条件化的单位展开（踩坑后修正）

报告里同一个金额有多种写法：`54448644 元`、`5444.9 万元`、`0.54 亿元`。
所以白名单必须做单位展开。但**展开不能无条件做**。

**踩的坑**：早期对所有数值都做 `×100` 和 `÷100`：

```python
# 错误版本：白名单被铺满整条实数轴
for v in out:
    for x in (v/1e4, v/1e8, v/1e6, v/100.0, v*100.0):
        out.add(x)
```

后果——编造的 `88.88` 竟然"擦边命中"了真实的 `89.83`（相对差 1.06%），
`43.7%` 命中了 `42.9`。**校验器形同虚设**。

**修正**：按数值量级区分语义，

```python
if a >= 1e3:          # 金额类：元 / 万元 / 百万元 / 亿元
    out.add(v/1e4); out.add(v/1e6); out.add(v/1e8)
elif 0 < a <= 1.0:    # 比例类：小数 / 百分数
    out.add(v * 100.0)
# 中间量（ROI、分位、1~1e3 之间的值）只保留原值
```

修正后白名单从"铺满实数轴"收敛为"语义明确的单位变体"，假阴性消失。

### 决策 4：三级降级（保证永不白屏）

| 情况 | 处理 | 用户看到 |
|---|---|---|
| 未配置密钥 | 直接模板渲染 | 完整报告 + "模板降级"标注 |
| LLM 超时/报错/限流 | 模板渲染 | 完整报告 + 失败原因写入审计块 |
| LLM 返回数字违规 | 注入违规清单重试 1 次 | 通过则采用 LLM 版 |
| 重试后仍违规 | **降级模板**，LLM 原稿另存 `.llm_rejected.md` | 正确报告 + 拦截说明 |

第 4 条是关键：**不采用有幻觉的稿子**。同时保留原稿供人工审阅——
万一 guard 判错了，分析师能立刻发现问题（而不是被静默丢弃）。

### 决策 5：按事实指纹缓存

报告内容只依赖 `facts`，所以用 facts 的 SHA256 前 16 位做缓存键：

- 数据变了 → 指纹变 → 重新生成
- 数据没变 → 直接读缓存，**不调用 API**（省钱、秒开）
- `--force` 可强制重算

Streamlit 页面首屏可以直接用缓存，用户点"重新生成"才走 LLM。

## 五、Prompt 工程要点

**System prompt 的 7 条铁律**（节选，关键是把"不许编造"写成**可执行规则**）：

```
1. 数字只能来自 facts。严禁自行计算占比、四则运算、估算，或引入外部数字。
2. 金额单位换算只允许一种口径：1 万元 = 10000 元。
3. 百分比保留 2 位小数，不要为了好看而四舍五入到整数。
4. 严格区分三类陈述：数据事实 / 模型推断 / 业务建议，不得混淆。
5. 必须如实转述 facts.risks，不得淡化 severity 为 high 的条目。
6. facts 里没有的信息，直接写「本次分析未覆盖」，不要编造。
7. 不要出现「作为一个AI」「以上由AI生成」等自我指涉表述。
```

**几个设计要点**：

- **"不许编造"必须可执行**。只说"不要幻觉"没用，要给出**换算口径**和**保留位数**，
  否则 LLM 会在"该保留几位"上自由发挥，反而制造出校验不通过的数字。
- **强制分层陈述**。LLM 最容易犯的错是"把模型推断说成数据事实"。
  要求它显式区分，能让报告在业务上站得住。
- **逼出局限**。要求如实转述风险清单，且不允许淡化 high 级条目——
  这是专业分析报告和营销软文的分水岭。
- **重试用 assistant 历史 + 违规清单**。把 LLM 自己的稿子和具体违规数字一起喂回去，
  比重新生成一次的修复率高得多。

## 六、实测：三条路径全部验证

因为环境未配置 LLM 密钥，我用 `LLM_MOCK=1` 的离线模拟模式验证完整链路
（模拟回复 = 模板文本，可注入幻觉）。

| 场景 | 命令 | 结果 |
|---|---|---|
| **A. 无密钥降级** | `python src/stage4_report.py` | 模板报告 4,399 字符，标注"模板降级" ✅ |
| **B. LLM 正常** | `LLM_MOCK=1 ... --force` | 检查 102 个数字 → 97 精确 + 5 舍入 + **0 违规** → 采用 LLM 版 ✅ |
| **C. LLM 幻觉** | `LLM_MOCK=1 LLM_MOCK_FABRICATE=1 ...` | 检查 104 个数字 → **2 处违规被拦** → 重试仍违规 → 降级模板 + 另存被拒稿 ✅ |

场景 C 的拦截明细（`stage4_guard.json`）：

```json
{
  "source": "template",
  "guard": {
    "checked": 104, "exact": 97, "rounded": 5, "fabricated": 2,
    "fabricated_detail": [
      {"原文": "88.88",  "最接近白名单值": 89.8305, "上下文": "据行业基准，同类出海游戏的整体 ROI 约为 88.88"},
      {"原文": "43.7%",  "最接近白名单值": 42.9,    "上下文": "提升到 6455 万元，提升 43.7%"}
    ]
  }
}
```

两类幻觉（**编造外部基准**、**记错真实数字**）都被抓住。

## 七、踩坑记录（7 个，全部定位修复）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 编造的 `88.88` 通过校验 | `expand_units` 无条件做 ×100/÷100，白名单铺满实数轴 | 按量级条件化展开 |
| 2 | 编造的 `7.777` 通过校验 | `classify` 用 ±0.51 绝对容差，被 `7.5` 放行 | 绝对容差只用于小整数通道 |
| 3 | **合规文本**被判违规 2 处 | 事实指纹 `db2f7b02750b2314` 被数字正则切出 `02750`、`2314` | 跳过 hex 串与行内代码 |
| 4 | **合规文本**被判违规 1 处 | 模板自己算了"边际效率 3.96 倍"（3.156/0.798），该值不在 facts 里 | 去掉模板中的除法，改为直接引用事实值 |
| 5 | 报告推荐的档位收益张冠李戴 | 把"弹性宽度 0.4"当成 ±40%（实际是 ±20%） | 明确映射：宽度 0.8 = ±40%，0.4 = ±20% |
| 6 | 重试时 prompt 重复 | `chat()` 在 history 之外又追加了一次 user 消息 | `user=""` 时不追加 |
| 7 | **阶段 1 图与阶段 2 数据不一致** | `data/processed/*.csv` 是旧版数据生成器的导出（周均花费 9.2 万 vs 现在 20.2 万），EDA 图也是旧的 | 阶段 4 改为 `generate_game_data()` 现算；重跑阶段 1 刷新图与数据 |

第 7 条是最有价值的发现：**下游拿到的数据产物过期了，而上游代码已经改了**。
它由"报告里总花费 7,693 万 vs 阶段 3 的 1.67 亿对不上"暴露出来。
这类问题不跑端到端就发现不了。

## 八、局限（诚实声明）

1. **白名单校验不是 100% 拦截**。它有容差（1%），编造数字若恰好落在某个事实值 1% 内会漏网。
   它是一层"防呆"，不是"证明"。真正的保障是 Prompt 铁律 + 校验 + 降级三层叠加。
2. **语义层面的错误无法自动校验**。LLM 可能"每个数字都对，但把因果说反了"。
   这类问题需要人工审阅——所以报告保留了事实指纹和 facts.json，可逐句溯源。
3. **缓存键只含 facts，不含 prompt 版本**。修改提示词后需要 `--force` 才会生效。
4. **风险清单（risks）是人工撰写并固化在代码里的**，不是从数据自动推导的。
   这是刻意的：局限声明需要人的判断，且必须稳定（不能每次生成都变）。

## 九、面试问答

**Q1：为什么要自己做校验，不直接相信大模型？**

因为 LLM 的失效模式是"看起来很对"。它写"行业平均 ROI 约为 4.2"时语气和写真实数字一样自信。
如果我直接把它的输出发给市场部，业务方按一个编造的基准做预算，就是事故。
我的做法是把"数字"和"叙事"彻底分开：所有数字由确定性代码算出（可审计、可复现），
LLM 只负责组织语言；它的输出再过一遍白名单校验，每个数字都要能在事实文件里找到依据。

**Q2：白名单校验具体怎么做的？**

三步。一，从 facts 递归收集所有数值，并按语义做单位展开（金额类展开元/万元/亿元，
比例类展开小数/百分数，中间量不展开）。二，用正则抽出报告里的每个数字。
三，逐个比对，分三级：相对误差 < 0.3% 算精确命中，< 1.0% 算舍入偏差，超过就是无依据。
这两个阈值是实测校准的——真实舍入误差都在 0.3% 以内，编造数字都在 8% 以上，中间留了足够的余量。

**Q3：如果校验没通过怎么办？**

先自动重试一次，把违规数字的清单和模型自己的原稿一起喂回去让它修订。
重试后仍违规，就**降级为模板报告**——宁可要一份朴素但数字正确的报告，也不要漂亮但错的。
同时把 LLM 的原稿另存为 `.llm_rejected.md`，万一我判错了，分析师能立刻发现。

**Q4：怎么保证 Streamlit 不会白屏？**

三层降级：没配密钥直接走模板；调用失败（超时、限流、报错）也走模板；
数字违规还是走模板。模板是纯代码渲染的完整六节报告，业务信息一点都不少，
只是没那么"会说话"。所以报告页永远有内容可看。

**Q5：缓存是怎么设计的？为什么这么做？**

用 facts 内容的 SHA256 前 16 位做缓存键。因为报告的全部内容只依赖 facts——
数据没变，报告就不该变。这样 Streamlit 首屏可以直接读缓存秒开，
只有用户主动点"重新生成"才调用 API，成本可控。

**Q6：这个流程你觉得还有什么风险？**

两个。一是白名单有 1% 容差，编造数字若恰好落在某个事实值附近会漏网，
所以它只是"防呆"不是"证明"，最终还需要人审。
二是语义层面的错误（数字都对但把因果说反）无法自动校验——
这也是我保留 `stage4_facts.json` 和事实指纹的原因，保证每一句话都能溯源到原始数据。
