# 阶段 9：预算优化页与决策报告页

> 阶段 3 已经算出了"钱该怎么分"。阶段 9 要解决的是另一个问题：
> **怎么让一个不懂贝叶斯的人，在 3 分钟内看懂"该不该信、该动多少、动了能拿多少"。**
>
> 这一页承载整个项目**最有决策价值的产出**，也是面试演示的主场。

---

## 1. 这一页的核心主张

面板上最容易被误读的产出，是"一个最优分配数字"。本项目的主张是：

> **交付物不是「一个最优分配数字」，而是「弹性-收益曲线」。**

原因是一个数学事实：在带硬边界的最优化问题里，**最优解几乎全部卡在边界上**。
本机实测（±40% 约束）：5 个渠道里有 4 个卡在上下限，唯一"自由"的那个渠道，
它的取值其实是预算守恒算出来的**算术残差**，不是模型对它的测算结论。

这意味着：

| 看起来重要 | 实际决定结果 |
|---|---|
| 模型小数点后第几位 | ❌ |
| MCMC 抽样数 6000 还是 8000 | ❌ |
| **允许每个渠道调多少**（业务方拍板） | ✅ |
| **总预算给多少** | ✅ |

所以整页的组织逻辑是：**先回答"钱该往哪挪"，再把"允许调多少"这个业务旋钮交到用户手里。**

## 3. 六个 Tab：每个对应一个业务问题

### 3.1 「钱该往哪挪？」—— 边际回报 + 响应曲线

回答"当前多投 1 元，哪个渠道回报最高"。本机实测（窗口内）：

| 渠道 | 边际回报 | 94% 区间 | 平均 ROI | 读法 |
|---|---|---|---|---|
| TikTok | 3.156 | [3.094, 3.221] | 1.829 | 明显高于盈亏线 |
| Google | 2.216 | [2.154, 2.279] | 1.211 | 高于盈亏线 |
| KOL | 1.632 | [1.443, 1.816] | 0.924 | 高于盈亏线，但平均 ROI < 1 |
| Facebook | 1.441 | [1.323, 1.556] | 0.679 | 溢价有限 |
| YouTube | 0.798 | [0.664, 0.929] | 0.413 | **低于 1，加投即净亏** |

设计要点：

* 颜色按**决策方向**给（红=该加投、绿=该收缩），不是按渠道给色 —— 颜色本身要携带信息。
* 误差棒是边际回报的 94% 后验区间。**区间跨越 1.00 的渠道标注"证据不足"**，此时优先看业务判断。
* 特别提示"边际回报是**局部斜率**，不是平均 ROI"。所以会出现"平均 ROI 很高但边际回报已很低"的渠道（KOL 就是接近这种状态）——那意味着它已经投放充分了。
* 页面下方给出整条响应曲线网格，回答**未来**的问题：再加 50% 会不会饱和？

### 3.2 「具体怎么分？」—— 分配对比 + 约束体检表

±40% 约束下的最优分配（万元）：

| 渠道 | 当前窗口预算 | 优化后 | 变化 | 卡边界 |
|---|---|---|---|---|
| Facebook | 262.60 | 157.56 | −40.00% | 下限 |
| Google | 428.86 | 518.41 | +20.88% | — |
| TikTok | 369.40 | 517.16 | +40.00% | 上限 |
| YouTube | 199.22 | 119.53 | −40.00% | 下限 |
| KOL | 131.44 | 78.87 | −40.00% | 下限 |

**这里最容易误读的一处，必须点破**：

Google 那 +20.88% 不是模型算出来的。四个渠道被推到边界后，
Google 的取值 = 总预算（1391.53 万元）− 其余四个渠道边界值之和（873.12 万元）。
它是**预算守恒的算术残差**。实测证据：给 12 个不同后验样本各求解一次，
其他四个渠道的取值在元级别上完全不变（因为它由算术式钉住）。

所以页面上把它显式标出来（`residual_channel` / `residual_note`），
并在结论卡里紧跟结论、不沉到页面底部 —— 否则用户会照着那个数字去调投放。

约束体检表另外给出四条判据：

| 判据 | 本次结果 | 说明 |
|---|---|---|
| 优化窗口 | 2025-10-05 ~ 2025-12-28（13 期） | 前 6 期作 Adstock 残留预热 |
| `channel_scales` 已挂载 | ✅ | 不挂载会静默回退 1.0，返回假最优解 |
| 数值优化收敛 | ✅ nit=47 | nit≤2 是"没搜索"的信号 |
| 解的角点占比 | 4/5 | 角点越多，结果越由"边界宽度"决定 |
| 残差渠道 | Google | 其幅度是算术结果，不能当建议读 |

### 3.3 「该接受多大调整？」—— 弹性-收益曲线（本页核心）

对每一档"允许的调整幅度"各求解一次最优分配：

| 允许调整 | 预期贡献（万元） | 提升 | 收敛 |
|---|---|---|---|
| ±5% | 5,282.39 | +1.22% | ✅ |
| ±10% | 5,351.28 | +2.54% | ✅ |
| ±20% | 5,505.69 | +5.50% | ✅ |
| ±40% | 5,888.73 | +12.84% | ✅ |
| ±60% | 6,386.05 | +22.37% | ✅ |
| 无约束（理论上界） | 8,747.45 | +67.62% | ✅ |

单调性已断言（放宽约束不应让收益变差）。

这张图回答的不是"最优是多少"，而是**"我们愿意接受多大调整，能拿多少增量？"** ——
这是业务方真正能拍板的东西，也是这一页与"跑个优化器输出一个数"的本质区别。

页面对 ±20% 与 ±40% 给出明确的业务话术：

* **±20%（当月可执行）**：对渠道团队编制与平台关系冲击很小。
* **±40%（1~2 个季度逐步到位）**：需先验证模型预测方向。

### 3.4 「预算整体变了怎么办？」—— 情景分析

| 情景 | 总预算（万元） | 提升 |
|---|---|---|
| ×0.8 | 1,113.22 | +12.95% |
| ×1.0 | 1,391.53 | +12.84% |
| ×1.2 | 1,669.84 | +11.87% |

三个情景的提升幅度相差 **1.08 个百分点** → 结论对总预算规模不敏感，业务上比较稳。

**一个容易写错的地方**：情景下"当前分配"必须**按同一倍数缩放**，
否则比较的是"新版预算 vs 旧版预算"，而不是"新预算下的优化 vs 新预算下的维持现状"。

### 3.5 「结论有多稳？」—— 后验不确定性 → 分配

把后验不确定性完整传导到最优分配：抽 N 个后验样本，每个样本走一次**完整的**
`set_posterior` + `allocate_budget`（不是用简化曲线估算）。

这一节最重要的产出**不是标准差**，而是**每个渠道的"方向"**：

| 渠道 | 卡下限 | 卡上限 | 未卡边界 | 方向 | 标准差 |
|---|---|---|---|---|---|
| TikTok | 0 | 12 | 0 | **结构性加投** | ~1e−9 元 |
| Facebook | 12 | 0 | 0 | **结构性减投** | ~2e−10 元 |
| YouTube | 12 | 0 | 0 | **结构性减投** | 0 元 |
| KOL | 12 | 0 | 0 | **结构性减投** | 0 元 |
| Google | 0 | 0 | 12 | 算术残差 | ~8e−10 元 |

为什么必须把上下限**分开**数：抽样数降到 6 时，Facebook 出现 **5 次卡下限 / 1 次卡上限** ——
它的标准差高达 78 万元，看起来"在动"，**方向其实是乱的**。
只看"卡边界次数"或"标准差"，会把这种情况误判为"很稳"。

所以页面上把方向单独说清楚，并给出可执行的判断：
**抽样数不足时，某些渠道的方向还没被数据定下来，此时应提高抽样数或按业务刚性处理。**

另外页面还解释了"接近零波动"的**结构性原因**：4 个渠道被推到边界、只剩 1 个自由，
而那一个的取值由守恒式直接决定 —— 换任何后验样本等式都成立。
所以这不是"模型很确定"，而是**约束把答案钉死了**。

## 4. 三条硬性要求怎么落地

### 4.1 长任务耗时长 → 后验子集加速 + 安全阀

**问题**：单次 `allocate_budget` 要在「后验样本 × 决策期数」上做矩阵运算。
全量 6000 样本 × 13 期 ≈ 10 秒/次，而本页要跑十几次
（5 档弹性 + 1 次无约束 + 3 个情景 + 主方案）→ 用户要等 1~2 分钟。

**A/B 实测（13 期窗口，±40% 约束）**：

| 后验来源 | 单次耗时 | `nit` | 最优分配（万元） | 提升 |
|---|---|---|---|---|
| 全量 6000 抽样 | 9.73s | 49 | 157.6 / 518.4 / 517.2 / 119.5 / 78.9 | +12.830% |
| 子集 300 抽样 | 0.38s | 52 | 157.6 / 518.4 / 517.2 / 119.5 / 78.9 | +12.865% |
| 子集 500 抽样 | 0.37s | 47 | 157.6 / 518.4 / 517.2 / 119.5 / 78.9 | +12.839% |
| 子集 1000 抽样 | 0.51s | 49 | 157.6 / 518.4 / 517.2 / 119.5 / 78.9 | +12.843% |
| 子集 2000 抽样 | 0.67s | 47 | 157.6 / 518.4 / 517.2 / 119.5 / 78.9 | +12.837% |

**逐渠道分配完全一致（最大偏差 0 元），快约 25 倍。**

**为什么这样是安全的**：`allocate_budget` 是**点估计**优化，用的是响应曲线的后验均值；
几百分样本的均值早已收敛到与全量无差别。

**但有两条边界必须说清楚，否则这就是在偷工减料**：

1. **只加速点估计。** 可信区间（`evaluate_response_distribution`）
   与稳健性检验要的是后验的**分布形状**，必须用完整样本 —— 它们**不在**加速区内。
2. **有安全阀。** 若子集求解出现 `nit≤2`、未收敛、或**并列解**（假优化的三个信号），
   自动退回全量后验重解一次，并在页面上提示。

加速通过 `fast_solve()` 上下文管理器实现，**进出对称**：

```python
with fast_solve(opt, idata, k=500) as fs:
    main = optimize_budget(opt, cfg, hist_total, ...)   # 走子集，快
    sweep = sweep_bounds(...); scen = scenarios(...)
# 出了 with 自动恢复全量后验
dist = response_distribution(opt, cfg, main["budgets"])  # 走全量，准
```

`opt` 是会话级共享对象（来自 `cache_resource`），**只进不出会让后续所有
不确定性分析悄悄拿到子集**——那是给区间注水，且完全不报错。
所以用 `try/finally` 兜住，异常路径也不会漏（T42 里有专门的断言验证这一点）。

**最终效果**：页面点"开始求解" → **4.4 秒**出结果（原来要 60~120 秒）。

## 5. 踩的坑与根因

### 坑 1 ★ `channel_scales` 静默错配（本页最关键的坑）

**根因**：库内 `mmm.py:3090` 写

```python
channel_scales = getattr(self, "_channel_scales", 1.0)
```

而 `MMM` 对象**默认没有这个属性**（`budget_optimizer.py:1096` 只在内部子对象上设 1.0），
于是静默回退到 1.0 → 货币与模型空间的量纲彻底错配。

**换算链**（阶段 3 已闭环验证）：

```
X 列 = 花费 ÷ 渠道周均
channel_scale = max(X 列)（库内 DataDerivedScaling(method="max")）
⇒ channel_scale × 渠道周均 = max(训练期花费)
```

所以挂 `max(花费)` 与库内换算完全一致。

**实测后果（13 期窗口 + 单渠道 ±40%，与页面实际跑的口径一致）**：

| 情形 | `nit` | 提升 | 分配（万元） |
|---|---|---|---|
| ✅ 挂载 | 50 | **+12.8301%** | 157.56 / 518.41 / 517.16 / 119.53 / 78.87 |
| ⛔ 未挂载 | 2 | **+0.0000%** | 309.53 / 309.53 / 309.53 / 278.91 / 184.02 |

注意 **`success=True`**：优化器认为自己成功了，只是没找到任何增量。

两个值得警惕的信号：
1. **提升数值上恰好为 0**（跑完一圈一个增量都没找到）；
2. **边际回报完全不同的渠道拿到了逐位相同的预算** —— Facebook / Google / TikTok
   三者逐位相同。在正确的目标函数下，这是**测度为零**的事件。

阶段 3 在无约束口径下也复现过一次（更极端）：不挂载 → `nit=1`、
分配 `[278.28]×5` 万元、提升 −0.00%。同一个根因，随窗口与约束换了个面目。

**修复与防御**：

* 建模阶段统一在 `assemble()` 里挂载（`fit` / `pretrained` / `cache` 三条路径全覆盖），
  并加 `scales_ok` / `scales_error` 标记。
* 优化页在调用前再挂一次（`ensure_channel_scales`），并做体检
  （`channel_scales_health`：全是同一个值 = 可疑）。
* `optimize_budget()` 内置**并列解检测**：一旦出现逐位相同的分配，
  直接在结论区报警，而不是等用户自己看出来。

> 一个关键教训：**这类 bug 只能靠对照实验发现，靠读代码很难察觉。**
> 所以页面把它做成了可点击的按钮，把"假优化"的样貌直接摆出来。

### 坑 2 无约束求解不能传 `(0, inf)`

```python
bounds = {c: (0.0, float("inf")) for c in channels}
r = opt.allocate_budget(total_budget=tb, budget_bounds=bounds)   # ❌ 会不收敛
r = opt.allocate_budget(total_budget=tb, budget_bounds=None)     # ✅
```

传 `[(0, inf)]` 会让 SLSQP 的边界矩阵出现 `inf`，数值条件变差、容易不收敛。
对外展示的 `bounds` 仍用 `(0, +inf)`（语义是"只受物理约束"），但**传给库的必须是 `None`**。

### 坑 3 角点判定的容差不能用 `inf` 上界算

无约束时上界是 `inf`，若直接拿它算 `atol`，`atol` 就是 `inf`，
于是**所有渠道都被误判成"卡在上限"**。正确做法只用有限上界定容差：

```python
_fin_hi = hi_v[np.isfinite(hi_v)]
_span = float(_fin_hi.max()) if _fin_hi.size else float(np.max(b))
_atol = 1e-6 * max(1.0, _span)
at_hi = np.isclose(b, hi_v, rtol=CORNER_TOL, atol=_atol) & np.isfinite(hi_v)
```

### 坑 4 ★ `st.status()` 的容器没有 `.step() / .done() / .fail()`

```python
box = st.status("正在求解…")
box.step("第一阶段")     # ❌ StreamlitAPIException: not a valid Streamlit command
box.done("完成")         # ❌
box.fail("失败")         # ❌
```

streamlit 1.65 实测 `StatusContainer` 只有 `update(label=, expanded=, state=)` 与
`write / progress / markdown / error` 等方法。

**这个坑的可怕之处**：页面**首次渲染完全不报错**，只有真正点到那个按钮才抛异常。
而且它一次命中**三个页面**（建模页 / 优化页 / 报告页都写了同样的错误调用）。

**修复**：收口到 `core/ui.py` 的 `StatusBox`（带能力探测），
`core/cache.py` 的 `TaskStatus` 改为它的别名 —— **同一件事有两份实现，就一定会有一份是错的**。

### 坑 5 ★ 跨行三元表达式会让 `st.info` 抛 `SyntaxError`

```python
ui.dataframe(pd.DataFrame(f.robustness)) if f.robustness else st.info(
    "本次未运行稳健性检验")
```

streamlit 的 `st.write` / `st.info` 会去 `ast.parse` **调用方的源码行**来推断变量名。
表达式跨行时，那一行本身就是不完整的 Python →
`SyntaxError: '(' was never closed` → 整个页面挂掉。

改成显式 `if/else` 即可。同样只在真正渲染到该分支时才暴露。

### 坑 6 可信区间的"94%"被自己的校验器判为编造

报告模板固定会写"增量 94% 可信区间为 …"。数字校验器把 `94` 当成数据值，
与白名单里最近的 `92.403` 相比（相对误差 1.73% > 1%）→ 判为**无依据** →
**任何正确提到可信区间的报告都会被降级成模板**（静默的假阴性）。

修复：把置信水平登记进白名单（`src/report_facts.py` 的"通用安全值"）。
放在 `allowed_numbers()` 而不是 `ReportFacts.meta` 的默认值里，
因为 `meta` 由磁盘/会话两个构建器各自**整体赋值**，写在 dataclass 默认值里会被覆盖掉。

### 坑 7 稳健性必须走官方 `set_posterior` 路径

最初我用"简化 Hill 口径逐样本重算"做稳健性，结果分布系统性偏离点估计 ——
因为简化口径忽略了 Adstock 时序与 carry-in，那是在检验**另一个目标函数**，
得到的"稳健性"没有意义。

正确做法：对**整份 `idata`** 切片后 `set_posterior()`：

```python
one = idata.isel(chain=[ci], draw=[di])   # 不能传 .posterior —— 缺 group 会 KeyError
opt.set_posterior(one)
r = opt.allocate_budget(total_budget=total, budget_bounds=bounds)
```

### 坑 8 决策期数不能贪多

单次求解成本与决策期数近似成正比。初始设 `MAX_DECISION = 26`，
单次 12~17 秒、整页 60~120 秒 —— 不可接受。
降到 **13 期（一个季度）** 后结论不变（阶段 3 用的就是 13 期），总耗时减半。

## 8. 面试可讲的三个点

1. **"我没有交付一个最优分配数字，我交付了一条弹性-收益曲线。"**
   因为在硬边界下最优解全卡角点 —— 我实测 5 个渠道里 4 个卡边界，
   第 5 个的取值还是算术残差。所以真正值得谈的是"业务方愿意让渠道调多少"。
   ±20% 只能拿到 +5.5%，±40% 拿到 +12.8%，放开到无约束是 +67.6%。

2. **"我抓住了三个静默错误 —— 它们不报错、有输出、但结论无意义。"**
   - `channel_scales` 未挂载：`success=True`、提升恰好 0、多个渠道拿到逐位相同的预算；
   - `st.status()` 的容器没有 `.done()`：页面首次渲染正常，**点了按钮才崩**；
   - 跨行三元表达式：`st.info` 解析调用方源码时抛 `SyntaxError`。
   三个都是靠**对照实验 / 无头渲染测试**发现的，靠读代码察觉不到。

3. **"我把'快'和'准'的边界划清楚了。"**
   点估计求解走 500 抽样子集（25 倍加速、分配偏差 0 元），
   可信区间与稳健性检验坚持走完整后验，
   并给子集配了"`nit` 崩塌 / 未收敛 / 并列解"三个信号触发的自动退回全量安全阀。
