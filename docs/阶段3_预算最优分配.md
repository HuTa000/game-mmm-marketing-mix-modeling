> 目标：把阶段 2 训练好的贝叶斯 MMM，变成一个"该往哪个渠道加钱/减钱"的可执行决策。

**一句话**：从"描述过去"走到"指导未来"。

## 二、数学框架（面试要能讲清楚）

### 2.1 优化问题

```
maximize    Σ_c  贡献_c( 花费_c )
subject to  Σ_c  花费_c = B               （总额约束）
            花费_c^lo ≤ 花费_c ≤ 花费_c^hi    （单渠道上下限）
```

其中 `贡献_c(花费_c)` 就是阶段 2 学到的响应函数：

```
贡献_c(花费) = β_c · Hill( Adstock_α(花费) ; κ_c, slope_c ) × target_scale
```

### 2.2 为什么会有"最优解"而不是"全给最好的渠道"

因为 **Hill 函数是边际递减的**：

```
d(贡献)/d(花费) 随花费增大而减小
```

所以：钱投得越多，边际回报越低。当 A 渠道的边际回报降到和 B 渠道相同时，
再往 A 挪钱就不划算了 —— **最优解就是"各渠道边际回报相等"的那个点**（拉格朗日条件）。

> ⚠️ 重要认知：**数学最优 ≠ 业务最优**。见第五节。

### 2.3 响应函数三件套（每个都要能解释）

| 组件 | 含义 | 通俗解释 |
|---|---|---|
| **Adstock** `A_t = x_t + λ·A_{t-1}` | 广告的滞后累积效应 | "今天投的广告，明天还有余温" |
| **Hill 饱和** `1 − κ^s/(κ^s + x^s)` | 边际递减 | "头 100 万效果最猛，第 1000 万基本白花" |
| **β 系数** | 渠道的基准效率 | "同样条件下，tiktok 天生比 youtube 能打" |

## 三、⚠️ 踩过的五个坑（含根因与修复）

这部分是本阶段**最有含金量的内容** —— 都是官方文档没写、只有动手才会遇到的。

### 坑 1：`channel_scales` 不设置 → 优化器"假优化"（最隐蔽）

**现象**：
```
allocate_budget 返回 budgets = [2783062, 2783062, 2783062, 2783062, 2783062]  # 五个渠道完全相等
scipy_result.nit = 1                                                          # 只迭代 1 次
```
看起来"成功收敛"，实际是**梯度消失导致的均匀分配**。

**根因**（读源码定位）：
`MMM.budget_optimizer()` 内部：
```python
return BudgetOptimizer(
    ...
    channel_scales=getattr(self, "_channel_scales", 1.0),   # ← MMM 对象没有这个属性！
)
```
`MMM` 类**没有** `_channel_scales` 属性 → 回退到 `1.0`。
而我们的 `prepare_data` 做了额外除法（渠道列 ÷ 自身均值），
模型内 `channel_data` 存的是**双重缩放值**，不是原始货币。

参数含义（官方 docstring 原文）：
> `channel_scales`: "Per-channel scale factors used to convert **monetary budgets into the model's native units**."
> `spend_var_scales`: "a node stored scaled and left at the default 1.0 is **optimized in the wrong units, silently**."

**修复**：
```python
# 换算链：节点值 = 花费 / 渠道周均 / channel_scale = 花费 / max(训练期该渠道花费)
mmm._channel_scales = np.array([get_spend_series(df, c).max() for c in cfg.channel_cols])
```
**闭环验证**（必须做，否则不知道对不对）：
```
facebook  channel_scale × 渠道均值 = 1,116,566.8  vs  spend_max = 1,116,566.8  OK
google    channel_scale × 渠道均值 = 2,174,053.8  vs  spend_max = 2,174,053.8  OK
...（5/5 全部精确匹配）
```

修复后：`nit` 从 1 → 53，分配出现真实差异。

### 坑 2：`create_optimization_model` 需要 `xarray_dataset`

**现象**：`ValueError: Model must have a fitted 'xarray_dataset'. Call build_model / fit first.`

**根因**：我只从 pickle 还原了 `idata`，但 MMM 还有一份内部 `xarray_dataset`（训练 X 的 xarray 副本），
在 `build_model()` 时生成。`create_optimization_model` 依赖它来推断日期频率、渠道/控制变量坐标。

**修复**（省去重采样）：
```python
mmm.build_model(X, y)    # 只建结构，不采样，秒级完成
mmm.idata = idata        # 注入阶段 2 的后验
```

### 坑 3：`evaluate_plan` / `allocate_budget` 的 plan 是**货币单位**，且不能绕过

**现象**：手工调 `_pack_decision_vector(货币值)` 得到的结果与 `allocate_budget` 的 `scipy_result.fun` 对不上，
一度以为"优化后反而变差 -18%"。

**根因**：`pack` **不做单位换算**，它把输入直接当决策向量。
`channel_scales` 的换算发生在 `allocate_budget`/`evaluate_plan` 的**内部路径**里。
我手工绕过这条路径，等于自己算错。

**修复**：只用公开 API，且传带标签的 DataArray：
```python
plan = xr.DataArray(货币分配, coords={"channel": cfg.channel_cols}, dims=("channel",))
ev = opt.evaluate_plan(plan, total_budget=B)      # ✅
```
**一致性验证**（决定性证据）：
```
scipy_result.fun                  = -83,661,104.6160
evaluate_plan(budgets).objective  = -83,661,104.6160
一致？ True
```

### 坑 4：`budget_bounds` 过宽 → SLSQP 失败

**现象**：
```
MinimizeException: Optimization failed: Positive directional derivative for linesearch
```
出现在 `bounds = [0.5x, 2.0x]` 这类较宽边界上。

**根因**：可行域变大后，数值梯度在边界附近指向不一致，线搜索找不到下降方向。

**修复**：
```python
try:
    r = opt.allocate_budget(total_budget=B, budget_bounds=bnds)
except Exception:
    r = opt.allocate_budget(total_budget=B, budget_bounds=bnds, return_if_fail=True)
    if not r.scipy_result.success:
        print("⚠️ 未收敛，结果仅供参考，建议收窄边界")
```
**业务建议**：边界宽度控制在 ±50% 以内，既给优化留空间，又避免数值问题。

---

### 坑 5：`set_posterior` 必须传**整份 idata**，不能只传 `.posterior`

**现象**（稳健性检验时）：
```
KeyError: 'Could not find node at posterior'
```

**根因**：`set_posterior` 内部调 `_extract_dataset(idata, "posterior")`，即 `idata["posterior"]`。
如果传入的已经是 `idata.posterior`，再取 `["posterior"]` 就找不到。

**修复（正确写法）**：
```python
one = idata.isel(chain=[ci], draw=[di])   # 对整份 idata 切片 ✅
opt.set_posterior(one)
r = opt.allocate_budget(...)

# 循环结束后恢复
opt.set_posterior(idata)
```

**为什么这很重要**：官方 docstring 明确说明
> "Every later call swaps the draws in place, so a loop over many posteriors costs **one solve each rather than one compile each**."

这正是做后验稳健性检验的正确工具 —— 60 个样本约 30 秒完成，而不是重建 60 次优化器。

## 五、最重要的业务洞察：约束比数学最优更重要

### 5.1 无约束的答案是"废的"

无约束优化给出：**tiktok 拿满全部 1,392 万预算，其余四个渠道归零**。

数学上完全正确（tiktok 边际回报最高），业务上**完全不可行**：

| 约束来源 | 为什么不能砍到 0 |
|---|---|
| 团队编制 | 每个渠道有专人运营，裁撤有成本 |
| 账号权重 | 平台账号断投会掉权重，复投成本极高 |
| 平台关系 | 长期断投会失去议价权、返点资格 |
| 素材供给 | 素材/达人池需要持续投入维护 |
| 数据资产 | 断投后模型无法学到该渠道的新响应 |

### 5.2 所以真实的决策变量是"边界"

稳健性检验（59 组后验样本）给出了一个**反直觉但极重要**的结果：

```
渠道        点估计     稳健性中位数    点估计分位
facebook   157.6万  →  157.6万          93%
google     518.4万  →  518.4万          90%
tiktok     517.2万  →  517.2万         100%
youtube    119.5万  →  119.5万         100%
kol         78.9万  →   78.9万         100%
```

**三个渠道的分位 = 100%，箱体被压成一条线**（见 `stage3_5_robustness.png`）。

**这意味着**：
- 在硬边界下，最优解**总是卡在边界角点**
- 后验参数的不确定性**没有影响**"该往哪推"，只影响"推的理由有多强"
- **真正决定结果的不是模型精度，而是业务给的弹性范围**

**面试时可以这么讲**：

> "我做完优化后发现，稳健性检验里最优解全部顶在边界上。
> 这让我意识到，预算分配项目里，建模的精度不是瓶颈 ——
> **瓶颈是业务方愿意给多少弹性**。
> 所以我把交付物从'一个最优分配数字'改成了'一张弹性-收益曲线'，
> 让业务方自己选能接受多大调整，对应能多拿多少收入。"

这是从"调包侠"到"懂业务的分析师"的分水岭。

## 八、面试问答准备（阶段 3 部分）

**Q1：预算优化为什么不能全押 ROI 最高的渠道？**
> 数学上确实该全押（我们算出来是 +75.7%）。但业务上不可行：
> 团队编制、账号权重、平台关系、素材供给都有刚性。
> 所以真正的交付物不是"一个最优解"，而是"**弹性-收益曲线**"——
> 告诉业务方"你愿意给 ±20% 弹性拿 6%，给 ±40% 拿 14%，给全额拿 76%"。

**Q2：怎么保证优化结果可信？**
> 三个层面：
> ① **官方 API 一致性**：`evaluate_plan` 复现 `scipy_result.fun`，误差 < 1e-6；
> ② **与真值验证**：边际回报排序 vs 真实 ROI，Spearman ρ = +1.000；
> ③ **后验稳健性**：59 组后验样本重复优化，结果稳定在边界（说明结论不由噪声决定）。

**Q3：优化时遇到过什么坑？**
> 最隐蔽的是 `channel_scales` 默认 1.0。
> 库内部用 `getattr(self, "_channel_scales", 1.0)` 取值，但 MMM 类没这个属性，
> 导致货币单位与模型空间错配，优化器返回"均匀分配"+ `nit=1`——
> **看起来成功，实际完全没优化**。
> 我是通过"五个渠道预算完全相等"这个反常现象发现的，
> 然后用 `channel_scale × 渠道均值 == 训练期最大花费` 做了闭环验证。

**Q4：Adstock 在优化里怎么体现的？**
> 优化窗口是 25 周（6 周 carry-in + 13 周决策 + 6 周 carry-over）。
> carry-in 保留历史花费，让 Adstock 不至于"冷启动"；
> carry-over 承接决策期的余温。
> 所以即使决策期花费为 0，仍有约 6% 的贡献来自 carry-in 余温——
> 我在评估时把这块作为"常数底"单独扣除，避免虚增增量。

**Q5：为什么用 SLSQP 而不是梯度下降？**
> 因为问题带**等式约束**（总额固定）和**盒约束**（单渠道上下限）。
> SLSQP 专门处理这类约束优化，官方也是默认选择（`ftol=1e-9, maxiter=1000`）。
> 我还额外处理了它在宽边界下不收敛的情况，加了 `return_if_fail` 兜底和提示。

## 九、与阶段 2 的衔接

| 阶段 2 产出 | 阶段 3 如何用 |
|---|---|
| `saturation_beta / kappa / slope` 后验 | 构造响应曲线 |
| `adstock_alpha` 后验 | 窗口 carry-over 长度与响应动态 |
| `target_scale` | 缩放空间 → 元 的换算 |
| ROI 排序 | 与边际回报排序交叉验证 |
| `channel_scale` | 货币 → 模型空间换算 |

**一句话**：阶段 2 学出来的**参数分布**，在阶段 3 变成了**决策分布**。
