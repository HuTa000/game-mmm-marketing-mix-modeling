## 一、业务问题：为什么要把模型做成应用

阶段 0~5 产出了模型、结论、报告。但从"求职作品"的角度看，还缺一样东西：**别人能不能自己动手验证你做过**。

一份静态报告的问题在于：面试官只能"读"你的结论，不能"验"你的判断。而 MMM 恰恰是一个**结论高度依赖假设**的东西——先验怎么设、约束给多宽、窗口取哪段，都会改变数字。把这些做成可交互的控件，让面试官自己拖动滑块看结论怎么变，说服力远高于一张图。

所以本阶段要解决三个具体问题：

| 问题 | 后果 | 本阶段对策 |
|---|---|---|
| 用户拿自己的数据来，列名五花八门 | 一上传就报错，体验直接崩 | 别名匹配 + 编码/分隔符嗅探 + 分级校验 |
| 建模耗时 10~20 分钟 | 切一次页面就重跑，应用不可用 | 会话状态 + 三级缓存 + 依赖链失效 |
| 出错了只给一句"Error" | 用户不知道改哪里 | 所有问题带「是什么 / 为什么 / 怎么办」 |

## 二、架构决策：为什么把"算数"和"界面"彻底分开

这是本阶段最重要的一个设计，也是后面阶段 7~9 能快速推进的前提。

```
app/
├── streamlit_app.py          路由入口（st.navigation），侧栏品牌区与全局状态
├── core/                     ── 基础设施 ──
│   ├── paths.py              纯逻辑：项目根定位、产物扫描
│   ├── schema.py             纯逻辑：列名别名表、字段匹配
│   ├── data_io.py            纯逻辑：读取、校验、标准化  ← 本阶段核心
│   ├── state.py              运行时：会话状态 + 依赖链失效
│   ├── cache.py              运行时：三级缓存 + 进度反馈
│   └── ui.py                 运行时：主题、KPI 卡片、校验清单渲染
├── views/                    ── 页面 ──
│   ├── home.py               概览与数据（阶段 6 完成）
│   ├── data_eda.py           探索性分析（阶段 7 占位）
│   ├── modeling.py           建模与诊断（阶段 8 占位）
│   ├── optimize.py           预算优化（阶段 9 占位）
│   └── report.py             决策报告（阶段 9 占位）
└── selftest_core.py          数据模块离线自测（21 类场景）
```

**分界线**：`paths / schema / data_io` **完全不 import streamlit**。

这个约束换来两件很实在的东西：

1. **可自动化验证**。「上传的 CSV 到底能不能正确解析」是个纯逻辑问题，不该靠人肉在浏览器里点。分开之后，`selftest_core.py` 可以直接跑 21 类场景，一条命令出结论。
2. **不依赖浏览器调试**。Streamlit 的错误栈默认藏在页面里，改一行看一眼；纯逻辑层可以直接 `print` 和 `pytest`。

实践中这个决策立刻兑现了价值：本阶段发现的 **6 个真实缺陷里有 5 个**是靠离线自测抓到的，而不是靠点界面。

## 三、多页路由：为什么用 `st.navigation` 而不是 `pages/` 目录

Streamlit 有两种多页方案。传统做法是把页面放进 `pages/` 目录由框架自动发现；新做法是 `st.navigation` + `st.Page` 显式声明。

选后者的三个理由：

1. **页面标题与文件名解耦**。传统方案的侧栏标题就是文件名（`1_数据与EDA.py` → 显示成一串字符），想改成"探索性分析"就得改文件名。
2. **导航结构即业务结构**。可以把页面分组成 `① 开始 / ② 分析 / ③ 交付`，让面试官一眼看出项目的推进逻辑，而不是看到一个平铺的列表。
3. **入口脚本与页面在同一 session 中运行**。侧栏的品牌区和全局状态灯只需要在入口写一次，对所有页面生效——每个页面只需关心自己的内容。

顺带一个副作用：因为页面脚本共享进程，`st.session_state` 天然跨页共享，这是"切页不重跑建模"的实现基础。

## 四、数据模块：两条路径 + 分级校验

### 4.1 两条数据路径

| 路径 | 入口 | 特点 |
|---|---|---|
| 内置模拟数据 | `load_builtin()` | 调用 `src/data_generator.py`，**与阶段 2/3 完全同源**，带真值标注列（真实 β、衰减率、逐周真实贡献），可用于验证模型估得准不准 |
| 上传自己的数据 | `load_uploaded()` | 支持 CSV / Excel；自动嗅探编码与分隔符；自动匹配列名别名 |

**同源性是刻意设计的**：内置数据走 `generate_game_data()`，与阶段 2 建模、阶段 3 优化用的是同一个函数、同一个 seed。所以应用里看到的数字与文档里的数字**必然一致**，不会出现"演示环境与报告对不上"的尴尬。

> 顺带解决了阶段 4 发现的老问题：`data/processed/*.csv` 是旧版生成器的产物，直接读盘会导致口径差 2 倍。应用层统一走"现算"，彻底绕开这个坑。

### 4.2 列名容错：别名表

分析师拿到的表列名千奇百怪。同一个"Facebook 周花费"可能是：

```
facebook_spend / Facebook Spend / fb_cost / FB花费 / 脸书广告费 / meta
```

`schema.py` 为每个规范字段维护别名表，匹配时先把列名**归一化**（小写、去空格/下划线/括号/单位），再比对。匹配分两轮：

1. 别名表精确命中
2. **剥离花费类后缀**再比对（`facebook花费` → `facebook`、`KOL 投放 (元)` → `kol`）

实测覆盖率：

| 测试列名 | 识别结果 |
|---|---|
| `日期` | ✅ date |
| `Facebook Spend` | ✅ facebook |
| `google_cost` | ✅ google |
| `TikTok花费` | ✅ tiktok |
| `油管花费` | ✅ youtube |
| `KOL 投放 (元)` | ✅ kol |
| `收入` | ✅ revenue |
| `版本更新` / `节假日` | ✅ version_update / holiday |

### 4.3 校验分级：绝不猜、绝不白屏

所有问题收敛为 `Issue(level, code, title, detail, hint)`，三级：

| 级别 | 配色 | 含义 | 是否阻断 |
|---|---|---|---|
| `error` | 红 | 缺关键字段、文件读不出、行数不足 | **阻断**，不给结果 |
| `warning` | 黄 | 已自动修复（去重、补缺、归零、补时间轴） | 不阻断，但必须告知改了什么 |
| `info` | 蓝 | 识别说明（按什么规则匹配上的） | 不阻断 |

**核心原则：只报告、只修复可安全修复的问题；遇到 error 不猜、不编造。**

举例：用户上传的表没有收入列，正确做法是明确告诉他"没找到收入列，数值列候选有 X、Y"，而不是自作主张挑一列当目标——那样只会给出一个看似正常、实则完全错误的模型。

## 五、缓存策略：三级缓存，各司其职

| 层级 | 手段 | 存什么 | 为什么必须这样 |
|---|---|---|---|
| L1 会话状态 | `st.session_state` | 模型、优化结果、报告 | 跨页面切换保留 → **切页不重算**，体验关键 |
| L2 进程缓存 | `st.cache_data` | 数据、事实层、上传解析结果 | 可序列化；避免每次交互重算 |
| L2 进程缓存 | `st.cache_resource` | PyMC 模型对象 | **不可序列化**；`cache_data` 会做拷贝从而直接报错 |
| L3 磁盘缓存 | `outputs/reports/app_fit_*.pkl` | 拟合出的后验（idata） | 跨重启可用，避免重开应用又要等 10~20 分钟 |

两个容易踩的点：

**① 模型对象必须走 `cache_resource`。** `st.cache_data` 会对返回值做序列化拷贝，而 PyMC 模型内部含 PyTensor 计算图与编译后的函数，无法 pickle。用错层级不是"慢一点"，是直接抛异常。

**② 缓存键必须包含数据指纹。** `fit_cache_key(dataset_fingerprint, cfg)`：

```
指纹 = sha1(标准化后核心列的数值 + 行数 + 渠道数 + 来源)
键   = 指纹 + "-" + sha1(用户超参的排序 JSON)
```

少了这层，用户换了一份数据却命中上一次的缓存，会拿到旧模型的结论——**这是正确性问题，比崩溃更危险**，因为界面看起来一切正常。

## 六、会话状态与依赖链：一个正确性问题

跨页共享的重结果放进 `st.session_state`，并建立依赖链：

```
dataset  →  model  →  optimization  →  report
```

**上游一变，自动级联清空下游**：

```python
def invalidate_from(stage):           # stage ∈ {dataset, model, optimization}
    if stage == "dataset":       → 清 model / optimization / report
    elif stage == "model":       → 清 optimization / report
    elif stage == "optimization":→ 清 report
```

为什么这是正确性问题而不是体验问题：如果用户上传了新数据、但没有清空旧的优化结果，页面会展示"新数据的 KPI + 旧数据的优化方案"。这种自相矛盾的数字比崩溃更糟——用户可能真的据此做决策。

实现上，`set_dataset()` 会比较新旧数据的**指纹**，只有指纹变化才触发清空（同一份数据重复载入不会把已拟合的模型清掉）。

## 七、踩的坑（7 个真实缺陷，全部定位并修复）

### ① `Series.translate` 不存在 —— 只在脏数据下崩溃

```python
t = s.astype(str).str.strip()
t = t.translate(str.maketrans("０１２３４５６７８９．－", "0123456789.-"))
# AttributeError: 'Series' object has no attribute 'translate'
```

`str.translate` 是**字符串**方法，不是 Series 方法。诡异之处在于：数值列会走 `is_numeric_dtype` 的提前返回分支，所以**只有混入文字的列才会触发这条路径**。也就是说——干净数据永远测不出来，一遇到真实脏数据就崩。

修复：用 `Series.map(lambda v: v.translate(TABLE))`。

### ② 会计负数 `(1,200)` 被误判为"无法转换"

`_to_numeric` 先检测括号判断负数，但**没有剥掉括号**就交给 `pd.to_numeric`，后者对 `"(1200)"` 返回 NaN。结果是：本该识别为 −1200 的值被当成"脏数据"，触发 `COERCION` 而不是 `SPEND_NEGATIVE`，掩盖了真实语义（退款冲销）。

修复：检测出负号后立即剥掉括号，再转数值、再施加负号。

### ③ 周次序号兜底路径不可达

我原本的逻辑是：**别名匹配失败**才去找"1,2,3…编号列"合成日期。但 `week` 本来就在日期别名表里——所以列名叫 `week`、内容是整数的表，会被别名先命中，然后解析失败，最后报一个含糊的错误。

修复：改成**按结果判断**而不是按来源判断——别名命中的列如果解析成功率 <80%，同样进入序号兜底。并且兜底检测改成**按值判断**（是否连续整数序列），而不是按列名，这样列名叫 `period` / `期数` / `t` 也能识别。

### ④ `pandas 3.0 + pyarrow` 正则不支持 `\u3000` 转义

`t.str.replace(r"[,\s\u3000]", "", regex=True)` 报 `ArrowInvalid: invalid escape sequence: \u`。

pandas 3.0 默认用 pyarrow 作为字符串后端，其正则引擎不接受 `\uXXXX` 转义。修复：直接写字面字符 `[,\s　]`。

### ⑤ `_template_csv` 定义在调用点之后

Python 模块级代码**自上而下执行**。我把三个辅助函数写在文件末尾，但中间就调用了 `_template_csv()` → `NameError`。

这个坑很有意思：**代码读起来完全合理**（函数都在文件里），只有真正运行才会暴露。是 Streamlit 的 `AppTest` 抓到的。修复：把辅助函数整体移到调用点之前（用脚本重排，可验证）。

### ⑥ `use_container_width` 已弃用

Streamlit 1.65 提示该参数将在 2025-12-31 后移除，应改用 `width="stretch"`。

修复：不猜版本号，而是**探测运行时签名**：

```python
if "width" in inspect.signature(st.dataframe).parameters:
    FULL_WIDTH = {"width": "stretch"}
else:
    FULL_WIDTH = {"use_container_width": True}
```

新旧版本都能用，且不产生弃用警告。

### ⑦ 两处是"我的测试写错了"，但值得记录

- **T03 期望给 GBK 警告，实际没给**：因为测试用的基准数据**全是 ASCII 内容**（英文列名 + 数字），GBK 与 UTF-8 的字节序列完全相同，编码嗅探正确地识别为 UTF-8。**这是正确行为，不是漏报**。修正测试：改用含中文列名的数据。
- **T20 期望 60 行触发"历史过短"**：`MIN_ROWS_SOFT = 52`，60 行不该触发。修正为 40 行。

这两条说明：**断言写错和实现有 bug，症状完全一样（都是 FAIL）**。所以每条 FAIL 都要先问"是实现错了还是我期望错了"——本阶段 3 条 FAIL 里有 1 条是实现的锅。

## 九、面试问答

### Q1：为什么要把纯逻辑和 UI 分开？

**考什么**：是否理解"可测试性"是架构属性，不只是代码风格。

**怎么答**：因为我需要验证"上传的 CSV 能不能被正确解析"这件事，而它本质是个纯逻辑问题。分开之后我写了 21 类场景的离线断言，一条命令跑完；不分开就只能靠人在浏览器里一个个点，既慢又会漏。实际收益很直接：本阶段发现的 6 个真实缺陷里，5 个是离线自测抓到的，不是点界面点出来的。

**追问预案**：如果问"这有什么代价"——代价是数据层不能直接用 `st.cache_data` 装饰，得在外面包一层。我认为值得。

### Q2：缓存键为什么必须包含数据指纹？

**考什么**：是否理解缓存的**正确性风险**，而不只是性能收益。

**怎么答**：缓存键不带数据版本的话，用户换了一份数据、但配置没变，就会命中上一次的缓存，拿到旧模型算出来的最优分配。界面看起来一切正常，但结论是错的——这比崩溃危险得多，因为它不会被发现。所以我把标准化后数据（保留 4 位小数）的 sha1 和超参的排序 JSON 一起折进键里。

**追问预案**："那如果数据只改了一个小数位呢？"——指纹会变，缓存失效，重新拟合。宁可贵一点，不要错。

### Q3：模型对象为什么不能用 `st.cache_data`？

**考什么**：是否真的踩过坑，而不是背概念。

**怎么答**：`st.cache_data` 会对返回值做序列化拷贝来保证调用方改不到缓存里的对象。但 PyMC 模型内部是 PyTensor 计算图 + 编译后的函数，无法 pickle，会直接抛异常。所以模型对象必须走 `st.cache_resource`——它只存引用，不拷贝。

**追问预案**："那怎么保证用户改不到模型？"——约定不修改；真要改就从配置重建。代价是放弃了防御性拷贝，换来的是可运行。

### Q4：一个数据校验模块，你认为最关键的设计是什么？

**考什么**：有没有产品/工程判断力，而不只是会写 `if`。

**怎么答**：**分级 + 不猜**。分级是因为"缺收入列"和"有 3 个缺失值"对用户的意义完全不同，前者必须阻断，后者自动修就行但必须告知。不猜是因为 MMM 的结论对输入极度敏感——如果我自作主张挑一列当收入列，会给出一个看起来正常、实际完全错误的模型，用户还拿它做预算决策。

**追问预案**："那你怎么保证不猜的同时体验又不差？"——每条 error 都带 `hint` 字段，直接告诉用户"请提供形如 2023-01-02 的日期列，列名可用 date/日期/week"；另外提供一个模板 CSV 下载，让他有样可循。
