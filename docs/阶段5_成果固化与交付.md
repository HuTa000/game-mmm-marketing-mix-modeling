## 一、业务问题：为什么「做完了」不等于「交付了」

前面四个阶段解决的都是**分析问题**：怎么建模、怎么优化、怎么生成报告。
但一个求职项目还有一个绕不开的问题——**别人怎么看得到、看得懂、信得过**。

具体来说有三类受众，需求完全不同：

| 受众 | 想要什么 | 现在的痛点 |
|---|---|---|
| **面试官（初筛）** | 30 秒内判断这个项目值不值得细看 | 一堆散落的脚本和 CSV，看不出主线 |
| **面试官（深聊）** | 5 分钟内确认你是「真做过」还是「抄教程」 | 结论背后的推导过程藏在 70 个脚本里 |
| **业务方 / 同事** | 一页纸看懂结论与建议 | 只看得懂图，看不懂后验分布表 |

所以本阶段不是「整理文件」，而是**把技术产出转成三种可消费的形态**：

1. **一份能直接发出去的报告**（HTML，单文件自包含）
2. **一个能验证可复现性的代码仓**（主链路清晰、依赖明确、一键跑通）
3. **一套能扛住追问的表达材料**（简历段落 + 面试问答稿）

## 三、HTML 报告的设计决策

### 3.1 为什么是「单文件 + base64 内嵌图片」

这是最关键的一个决策。备选方案有三种：

| 方案 | 优点 | 致命缺点 |
|---|---|---|
| 多文件 HTML + 图片目录 | 体积小、加载快 | 发微信/邮件时容易丢图，对方只看到一个空框 |
| Markdown / PDF | 专业 | Markdown 没图；PDF 不能自适应手机 |
| **单文件 HTML + base64** ✅ | 一个文件搞定，离线可看，手机可读，可另存 PDF | 体积大（3.18 MB） |

**选第三个的理由**：面试场景下，这份材料的典型用法是
「微信发给面试官」或「上传到作品集链接」。**任何一个环节丢图，前面四个阶段的工作就白费了**。
3 MB 的体积在今天的网络环境下不构成障碍，而「丢图」的代价是灾难性的。

### 3.2 三个必须处理的显示问题

按项目硬性要求，网页应用必须处理「窄屏图表显示不全」。HTML 报告的具体处理：

| 问题 | 方案 |
|---|---|
| **窄屏表格溢出** | 所有表格包在 `.tw{overflow-x:auto}` 容器里，横向可滑，页面不撑破 |
| **窄屏字号过密** | `@media (max-width:720px)` 下调字号、KPI 网格从 4 列变 2 列、`420px` 以下变 1 列 |
| **打印丢背景色** | `@media print` 里用 `-webkit-print-color-adjust:exact` 保留封面渐变；`.fig/.kpi/.risk-item` 设 `break-inside:avoid` 避免图表被拦腰截断 |

### 3.3 数字从哪里来：复用事实层

报告的**所有数字都不是手写的**，而是通过 `report_facts.build_facts()` 统一获取——
这个模块在阶段 4 就已经建好，是各阶段 CSV 的唯一致口。

这样做的直接收益：**报告与结果文件不可能不一致**。
如果某个 CSV 更新了，重新跑一次 HTML 生成器即可，不需要人肉同步。

页脚还打印了**事实指纹**（`facts_hash()` 前 16 位）——任何数字变动都会改变指纹，
可以用来核验「这份报告对应的是哪一版数据」。

## 四、踩坑记录：HTML 转义的三连坑

这三个坑都不是「写错语法」，而是**规则没统一**导致的隐蔽错误。全部靠检查生成物发现。

### 坑 1：f-string 把公式里的 `{c,t}` 当表达式求值

模型公式写成：

```python
f"""... Adstock(x_{c,t}) ..."""     # NameError: name 'c' is not defined
```

**根因**：f-string 中 `{...}` 是插值语法，`{c,t}` 被当作元组表达式求值。

**修复**：把公式抽成模块级**普通字符串常量**（非 f-string）：

```python
FORMULA_MODEL = """<div class="formula">... Adstock(x_{c,t}) ...</div>"""
# 使用时：f"""...{FORMULA_MODEL}..."""
```

比写双花括号 `{{c,t}}` 更稳——因为公式里可能还有别的花括号（如 `A_{t-1}`），逐个转义容易漏。
**教训：凡是含代码/公式的块，都不要放进 f-string。**

### 坑 2：表格单元格的转义规则不统一

最初 `table()` 的实现是**表头转义、表体不转义**：

```python
head = "".join(f'...{md(h)}...')      # 表头走 md() 转义
tds.append(f'...>{cell}<...')         # 表体原样输出
```

这导致两个方向都会出错：

- 表体里的 `<span class='down'>✓</span>` 能正常渲染 ✅
- 但表体里的纯文本 `"< 1.01"` **不转义** → 浏览器把 `< 1.01` 当标签开始 → 显示错乱 ❌

**修复**：引入 `Safe` 标记类，统一规则为「**默认转义，标记跳过**」：

```python
class Safe(str):
    """标记：该字符串已是可信 HTML，表格渲染时跳过转义。"""
    __slots__ = ()

def H(s) -> Safe:
    return Safe(str(s))

# table() 内：
out = str(cell) if isinstance(cell, Safe) else md(cell)
```

调用侧：纯文本直接传，带 `<strong>` / `<span>` 的用 `H(...)` 包一层。

### 坑 3：双重转义（最容易漏）

修完坑 2 之后仍然出现 `&amp;lt;`，原因是**调用侧先 `md()` 转义了一次，`table()` 内部又转义一次**：

```python
rows = [[H(...), md(v)] for ...]   # ❌ md(v) 已经转义，table 里再转 → &amp;lt;
rows = [[H(...), v] for ...]       # ✅ 传原始文本，由 table 统一转义
```

**检查方式**：在生成物里搜索 `&amp;lt;`、`&lt;span`、`&lt;strong`，**这三个的字面量出现次数必须是 0**。
这是验证转义正确性的最快手段。

```bash
grep -o '&amp;lt;' outputs/reports/stage5_report.html | wc -l   # 期望 0
grep -o '&lt;span' outputs/reports/stage5_report.html | wc -l   # 期望 0
```

### 小结

> **转义 bug 的共同特征是「不报错」**——页面能打开、大部分内容正常，
> 只有个别字符显示成 `&lt;` 或整段错位。
> 所以**必须对生成物做机械化的字面量搜索**，而不能靠「打开看看差不多就行」。

## 五、代码仓整理策略

### 5.1 整理前的问题

`src/` 下有 **72 个 Python 文件**，其中真正构成主链路的只有 14 个。其余 58 个是：

- `probe_stage3a~k.py`（11 个）：阶段 3 的 API 探针，用于摸清 `BudgetOptimizer` 行为
- `verify_v2~v43.py`（42 个）：阶段 2 的逐版本验证脚本
- `verify_scaling.py` / `diag_scale.py` / `verify_official_contrib.py`（3 个）
- `exp_identifiability.py` / `verify_rc.py` / `verify_v36.py`（3 个，有复用价值）

**为什么必须整理**：面试官打开 `src/` 看到 72 个文件，第一反应是「这人在试错」，
而不是「这人有工程能力」。**整理本身就是信号**。

### 5.2 整理原则：移动而非删除

| 处理 | 文件 | 理由 |
|---|---|---|
| **保留在主链路** `src/` | 14 个 | 按阶段顺序即可复现全部结论 |
| **移入** `src/experiments/` | 3 个 | 结论已写进文档，但脚本有复用价值（可识别性实验、响应曲线验证） |
| **归档** `archive/dev_scripts/` | 55 个 | 一次性诊断，结论已固化到文档，保留供追溯 |

**为什么不直接删**：这些脚本是「我踩过哪些坑」的证据链，删了就回不来了。
归档目录在 README 里明确标注为「非主链路，仅供追溯」，既清理了视线又不丢失信息。

### 5.3 归档前必须先验证依赖

整理代码最大的风险是**删掉别人的依赖**。所以归档前先做了依赖扫描：

```bash
grep -nE "(mmm_core|response_curve|report_facts|...)" src/stage*.py | grep -E "^\S+:[0-9]+:\s*(from|import)"
```

结果证明主链路的内部依赖只有 8 条边，且**没有任何一条指向诊断脚本**：

```
data_generator  ← stage1_eda / stage2_model / stage3_optimize / mmm_core / report_facts
mmm_core        ← stage2_model / stage3_optimize / response_curve
response_curve  ← stage3_optimize
report_facts    ← stage4_report / report_templates
report_guard / report_prompts / report_templates / llm_client ← stage4_report
```

归档后跑 import 冒烟测试：**8/8 模块全部通过**。

## 六、简历与面试材料的设计逻辑

### 6.1 为什么简历要分三个版本

同一个项目，投不同岗位时**要突出的东西完全不同**：

| 版本 | 目标岗位 | 主线 | 关键词 |
|---|---|---|---|
| 技术版 | 算法 / 数据科学 | 方法论的严谨性 | 参数回收、可识别性、静默缺陷定位 |
| 业务版 | 商业分析 / 增长 | 决策价值 | 渠道排序、边际回报、弹性档位 |
| 一句话版 | 自我介绍开场 | 30 秒抓住注意力 | 一个数字（ρ = 1.000） |

**关键设计**：技术版里我把「定位并修复 3 个静默失效缺陷」单独列了一条。
这在技术面试里是**强信号**——它证明你不是在调用 API，而是在理解库的行为。

### 6.2 面试问答稿的结构逻辑

每道题按 **考什么 → 怎么答 → 追问预案** 三段组织，而不是简单给答案：

- **「考什么」**：理解面试官的意图，才知道该往哪个方向答。
  比如问「为什么用贝叶斯」，考的不是贝叶斯定义，而是**你的技术选型是否有理由**。
- **「追问预案」**：面试的真实形态是**连续追问**。预先想好第二层、第三层，
  才不会在第一层答完后被问懵。
- **标注 ★ 优先级**：26 题不可能都背下来，标出 8 道最可能被问且最能加分的。

### 6.3 最重要的一节：表述红线

材料里专门列了一节「表述红线」，因为**这个项目最大的风险不是答不出来，而是说错话**：

| 不要说 | 应该说 |
|---|---|
| 「提升了 14.37% 的收入」 | 「**预期**媒体贡献提升 14.37%（94% CI +638~728 万元）」 |
| 「证明了 tiktok 效果最好」 | 「在**带真值标注的仿真数据**上，ROI 排序与真值完全一致」 |
| 「做了因果分析」 | 「观测数据的统计推断，定位为决策支持」 |

**为什么这最重要**：MMM 的资深面试官一定会问「你怎么知道模型是对的」。
把仿真数据的结果说成真实业务结论，第一个追问就会露馅。
反过来，**主动说明「因为是仿真数据所以能验证参数回收」——这恰恰是加分项**，
因为它证明你理解 MMM 的根本困难（没有真值就无法验证）。
